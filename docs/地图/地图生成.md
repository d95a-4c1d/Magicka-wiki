该文档用于记录地图生成的具体流程，当流程有变动时，请及时同步

# 整体

从大到小，我们分为：

```
地形->区域->建筑群->区块
```
基本单位是正方形的区块，以 $8\times 8$ 为大小
暂定目前的地图大小为 $128 \times 128$ 区块

## 地形

为了保证整体地形高度的平滑性，我们统一使用一个Terrain对象

要生成地形，我们需要以下的控制图(默认都是0-1控制图)：

平缓程度：连续控制图，用FBM去生成，越接近于1说明此处的地形越平缓
叠加高度：一张简易的波形连续控制图，由平缓程度决定了波形的颠簸程度
山地：连续控制图，但是有随机撒种+Domain Warp生成，形式上类似于若干的平顶峰
最后要得到高度图，就直接拿 $\text{山地}\times \text{叠加高度} \times \text{常数}$

先暂时做这么多先

## 区域

区域又由若干的控制图决定，比如高温+湿度+平原=雨林之类的
先不管这么多，先大致做一个城市的区域

采用随机撒种，通过区域内的高度图是否平缓和一定的概率决定城市群的生成与规模

## 城市群

具体生成流程为

确定城市范围
→ 划分功能区
→ 摆放关键大模板 / 大建筑
→ 生成主干道路
→ 生成次级道路 / 街区道路
→ 切分街区和地块
→ 在功能区内填小建筑

注意对高度图进行一定程度上的修改，使得其不要出现太过陡峭的部分
建筑的填充方式则使用预制的建筑模板，最后根据地形为区块设定权重，将城市间通过主干道连接即可

道路的生成方式采用spline

## 建筑模板与3D Tile约定

建筑模板用于描述一个可以被城市生成系统摆放的建筑单元。模板本身以Object空间的原点作为二维平面左下角，默认使用本地坐标的 $+X$ 方向作为宽度方向，$+Z$ 方向作为长度方向，$+Y$ 方向作为高度方向。

### 尺寸约定

一个区块由 $8\times 8$ 个tile组成，同时对应 $8\times 8$ 个Unity世界单位。

因此，默认情况下：

- 1个tile占据 $1\times 1$ 个Unity世界单位的平面面积
- 1个区块占据 $8\times 8$ 个Unity世界单位的平面面积
- 建筑模板的平面长宽以区块为单位记录
- 建筑模板内部的tile位置以tile为单位记录

建筑模板允许多层结构。模板内tile的逻辑位置使用三维整数坐标表示，例如 $(x,y,z)$，其中 $x$ 和 $z$ 表示平面网格位置，$y$ 表示高度层。

### 资源路径约定

MagicaVoxel导出的源文件放置在：

```text
Assets/Artset/Building/tiles
```

例如 `.obj`、`.mtl`、`.png` 等源资源应保留在该目录内。

可在Unity中直接实例化的tile prefab放置在：

```text
Assets/Perfab/Building/Tiles
```

可供地图生成系统摆放的建筑模板prefab放置在：

```text
Assets/Perfab/Building/Templates
```

### Tile与模板内容

建筑模板内部保存的不只是普通墙体、地板等tile，也可以保存门、机关、容器等特殊建筑部件。它们在模板编辑器中都以tile prefab的形式被放置，但可以通过脚本参数区分用途和后续行为。

每个tile prefab应挂载一个用于描述tile信息的脚本。该脚本至少需要支持：

- 该tile是否参与运行时mesh合并
- 该tile是否阻挡移动或寻路
- 该tile的碰撞盒参数
- 后续破坏效果、交互效果、门等个性化参数

初版中，tile的碰撞统一使用BoxCollider处理。

### 模板数据结构

建筑模板内部的tile数据按mesh chunk进行分桶保存，而不是用单个全量列表维护所有tile。

当前约定为：

- 序列化保存层使用 `TileChunk -> TileEntry列表`
- 每个 `TileChunk` 使用 `Vector3Int chunkKey` 标记所在分桶
- 每个 `TileEntry` 使用 `Vector3Int gridPosition` 标记单个tile在模板内的逻辑坐标
- 运行时和编辑时会从分桶数据重建 `Vector3Int -> TileEntry` 查询表
- 普通单格查询应通过 `Vector3Int` 直接查询，不应遍历整个模板的所有tile

这样做的原因是Unity默认不稳定支持直接序列化 `Dictionary`，因此保存层使用可序列化的chunk列表，而使用层恢复为类似C++ `map` / 哈希表的查询结构。

模板实体层级也应按chunk组织。当前约定是将tile实体放入模板对象下的 `Tile_Chunks/Chunk_x_y_z` 节点中，避免一个模板根节点下直接堆满所有tile实体。

### 编辑器约定

建筑模板应提供专用Editor编辑器，用于在Scene视图或Inspector中编辑模板内容。

编辑器需要支持：

- 设置模板占据的区块长宽
- 选择当前要放置的tile prefab
- 在三维网格中像搭方块一样放置tile
- 删除已有tile
- 调整tile朝向
- 切换当前编辑高度层
- 以Object空间原点作为左下角进行可视化

编辑器中显示的网格应遵循“1个tile = 1个Unity世界单位”的默认比例。

### 运行时优化约定

建筑模板在游戏运行时应自动执行一次初始化优化。初版目标是合并模板内可合并tile的mesh，以减少Draw Call和渲染对象数量。

MagicaVoxel导出的obj通常共享同一套调色板材质，因此在材质一致且tile允许合并时，可以将多个tile的Mesh合并为一个或少数几个Mesh。

需要注意：

- mesh合并只处理可合并的静态可视部分
- 仍需要保留特殊tile的脚本参数，供后续破坏、交互或门逻辑使用
- 初版可以先保留每个tile的BoxCollider，后续再考虑合并碰撞
- 不应把有独立运行时行为的tile强制合并掉

当前运行时优化采用chunk级别重建策略。tile被摧毁或恢复时，不重建整栋建筑的mesh，只标记该tile所在的mesh chunk为dirty，并在后续帧中按数量上限分帧重建。这样可以避免单个tile破坏造成整栋建筑重新合并的高开销。

### 当前实现进度

目前Unity工程中已完成以下初版脚本：

- `BuildingTile`
  - 维护tile目标对象、六方向朝向、硬度、耐久、是否可摧毁、是否阻挡移动/寻路、是否可参与mesh合并等信息
  - 修改朝向时会同步旋转目标模型
  - 摧毁/恢复时会切换碰撞和渲染状态，并通知模板刷新对应mesh chunk

- `BuildingTemplate`
  - 记录模板长宽高，约定1个区块为 $8\times 8$ tile
  - 使用 `TileChunk -> TileEntry列表` 保存模板内容
  - 运行时建立 `Vector3Int -> TileEntry` 查询表，支持按坐标直接获取tile
  - 将tile实体整理到 `Tile_Chunks/Chunk_x_y_z` 层级中
  - 支持按坐标造成伤害或设置摧毁状态
  - 支持按mesh chunk合并可合并tile的mesh，并在tile视觉状态变化时只重建对应chunk

- `BuildingTemplateEditor`
  - 已有第一版Scene视图编辑器
  - 支持选择tile prefab、选择朝向、选择高度层、放置/删除/吸取tile
  - 当前手感仍需要继续调整，后续重点应放在连续绘制、拖拽体验、层级切换、预览表现和误操作保护
